从运行引擎、数学建模、算法到应用整体重构；以多途径、多角度、可检验的科学方法研究相对随机选号的收益优势。不能用增加术语、补免责声明或跑过测试代替实现。大乐透和双色球需要直接进入日常使用与持续验证流程，而不是只在足球研究看板中附带展示离线结果。

用户已确认目标为“解决可靠优于随机选号的收益优势的方案，剩下的交由你去完成”。技术路线、实现和验证由本项目负责，无待补充的业务意图。

## 依赖顺序与验收草案

1. **数据与规则 →** 两个彩种统一保留期号、开奖时间、原始来源与版本；逐期奖金和奖池缺失必须可见，历史规则按期号适用。用已归档公告样本核对字段，不能将缺失奖金补成估计的实际收益。
2. **模型与选号 →** 将概率估计、选号偏好、票组组合优化分别定义输入输出；每个候选策略记录假设、训练区间、参数、版本及同成本随机基线。单注概率、任意奖覆盖和条件奖金不能混用同一评分。
3. **评估 →** 所有对外提供的策略通过同一套逐期向前评估；预算、追加费用、数据可用时间一致；固定验证窗口与比较族，保留失败模型和负收益结果。
4. **前瞻执行 →** 开奖前保存每期策略组合与随机对照；开奖后按对应期规则评分结算；重跑不改原预测、不重复计收益；更正公告留版本。该协议独立于已冻结的足球协议，不修改现有足球档案。
5. **应用 →** 大乐透/双色球可切换，主流程连接“本期数据 → 模型依据 → 预算与组合 → 开奖前登记 → 历史与前瞻成绩”；展示用户正在使用的真实引擎与证据，不能让新实验只存在于旁路报告。
6. **完整验证 →** 两彩种各运行一次完整用户路径，验证参数变更、预算不足、数据过期、失败重试、开奖结果修订、重启和单文件构建。最终分别报告工程完成度与收益优势证据，不把前者当作后者。

## 当前工作边界

按上述依赖顺序实施。新 index.html 成为数字彩主应用；原功能迁移至 number-tools.html 并保留原测试。前瞻协议在首次真实登记前冻结模型、预算、比较族及代码哈希。工程验证通过与可靠收益优势成立分别判定：收益结论必须来自固定协议下的新观察，不能由代码测试、号码覆盖、历史筛选或未经识别的浮动奖金替代。
